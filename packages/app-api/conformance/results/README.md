# Conformance results (run 7, conformance phase I2: 254-vector suite, suite increment I1 contract)

`conformance-matrix.md` / `.json` and `results.json` come from one invocation of the suite's own
command line against the JSON-RPC adapter in `../`; the files are regenerated by re-running it, never edited by hand.
Suite state run against: 254 vectors (framework incl. TIME-103..105, ceremony-vrc incl. 2PC-001..008, DIS, BND, CER-001..016, imported); the suite increment I1 contract: the clock capability, a declared window, the run salt and the vacuous-pass rule.
The adapter declares `clock` (it has an injectable clock; never `clockFree`) and its window, `capabilities.window` = 300 s maximum age, 60 s skew, 30 days expiry horizon,
read from the pipeline's own pinned constants, so it equals the profile pins: the matrix rows carry `window` (in `conformance-matrix.json`) with no window difference, and no fixture row is SKIP for a window difference.
Every run used the default random salt (each run's salt is stored in `results.json` as `salt`); a rerun with `--salt <value>` (the same value) reproduces ids and results exactly, and gave the same per-vector results as the random runs.
Every matrix cell is green (at least one anchor positive vector ran and passed, none failed), so there is no `*` vacuous-pass annotation.
The adapter declares `capabilities.ceremony.proposerApproves: false` (the stack's native model: a begin records no approval, every named
administrator co-signs) and the status task (`statusType`, `statusPayload`), so CER-014 pins the declaration, CER-015 and CER-016 run and CER-002 is SKIP.

## Rows

Two rows, `truststackers-agent-didkey` and `truststackers-agent-scidvh` (a `did:key` or the real `did:scid:vh`
connection identifier). Each merges two runs by the suite's rule (runs sharing `capabilities.implementation`): the attested
server (Tiers 1 and 2) and the non-attested server (Tier 1). Only the non-attested run executes the 16 vectors that assert
Tier 1 behaviour an attested server does not show; in the merge nothing is left uncovered for that reason.

| Column | Measured by | Binding |
|---|---|---|
| framework (ENV, RSP, ERR, ID, LIF, CTRL, TIME, DUP, PRF) | **Fixture carrier**: the suite's widget task served by a fixture handler behind the real pipeline, proof verifier, accepted-id store, signer and recorder. | https-binding (BND) | **Real listener, adapter-held tokens**: the agent's own `startBoundaryListener` on loopback, a real HTTP request, a static bearer-token to VID map held by the adapter (the agent's own listener is proof-only and does not map tokens). The carrier is the fixture widget. | https |
| two-phase-commit (2PC-001, 002, 006, 007, 008; 003..005 are in the row above) | **Real**: `issue` through the real `TransactionCoordinator` (durable log, `getOutcome`) and the real VRC receive participant. Faults are one-shot hooks in a participant wrapper (`conformance/two-phase.ts`): abort and voteNo end through the coordinator's own abort; `inflight` and `unknown` park the transaction in phase 1 (no decision logged), and are not told apart; `deliver:false` drops the reply after commit. | https for status assertions |

| ceremony-doc (CER), 2PC-003..005, TIME-103 | **Real handlers, fixture effect**: begin, co-sign, status and reset over the real pipeline, transaction coordinator, ceremony participant and store; the establishing effect is a fixture (unique community name). `ceremonyDeadline` is the participant's approval window; `ceremonyEffect` injects commit, fail (closed reason) or unknown at the effect (unknown leaves the ceremony pending and is answered a retryable indeterminate; `settle` processes the held approval again); `retained` reads the append-only record. The default run measures the native quorum model (`proposerApproves` false); the conformance server flag `--proposer-approves` switches the participant option on and declares `true`, and passes as well (CER-014 PASS), but is not what these results measure. | in-process |
